# ميزان الطبي — المراجع الوظيفية والمواصفات التنفيذية

**التاريخ:** 2026-11-16  
**الحالة:** مواصفات مرجعية وخطة تطوير، وليست إعلانا بأن هذه الميزات منفذة.  
**الإصدار المستهدف:** 0.2.x بعد إتمام واختبار المرحلة الأولى 0.1.0.

## 1. الهدف والنطاق

إنشاء نظام مالي للمستشفيات العربية يعمل على Windows عبر شبكة داخلية LAN متعددة المستخدمين، مع خادم ASP.NET Core وقاعدة PostgreSQL مركزية، وتطبيق WPF للموظفين. يستهدف المستشفيات والمراكز الصحية الصغيرة والمتوسطة في اليمن، ولا يتطلب اتصالا بالإنترنت أثناء التشغيل الداخلي. يعتمد إدخال البيانات بحسب صلاحية المستخدم، ويمنع الاتصال المباشر من أجهزة الموظفين بقاعدة البيانات.

هذه المواصفة لا تحول المشروع إلى سجل طبي إلكتروني شامل، ولا تعني اعتماد أي معيار طبي أو محاسبي أو قانوني بعينه. يجب اعتماد دليل الحسابات والتقارير وسياسات الاحتفاظ والصلاحيات من إدارة المستشفى والمحاسب المختص قبل التشغيل الفعلي.

## 4. القواعد المحاسبية الملزمة

1. **فرق الإيراد والتحصيل:** إجمالي الفواتير لا يساوي النقد المستلم. تقرير الإيرادات يتبع سياسة الاعتراف المعتمدة، وتقرير المقبوضات يتبع سندات التحصيل فقط. لا يضاف الدفع مرة ثانية إلى إيرادات الخدمات.
2. **سير المستند:** مسودة > مراجعة > اعتماد > ترحيل؛ بعد الترحيل لا تعدل العملية مباشرة. أي تصحيح يعتمد سند إلغاء أو مستند تسوية عكسية مع سبب وموافقة وسجل تدقيق.
3. **المعاملة الذرية:** عند اعتماد فاتورة أو قبض أو إلغاء يجب حفظ المستند وآثاره المحاسبية ضمن معاملة واحدة في PostgreSQL؛ نجاح جزئي غير مسموح.
4. **قيد متوازن:** مجموع المدين = مجموع الدائن؛ لا تقبل قيود بلا حساب، أو مبلغ صفري/سالب غير مناسب، أو تاريخ داخل فترة مقفلة، أو حساب غير صالح للترحيل.
5. **سلامة التحصيل:** إجمالي ما خصص للفاتورة لا يتجاوز رصيدها المستحق؛ المحافظة على تفرد رقم السند ومفتاح العملية لمنع تكرار الشبكة.
6. **عزل الصناديق:** لكل أمين صندوق مناوبة محددة، والمبالغ والنقدية تحت عهدته؛ إغلاق المناوبة يستلزم عد نقدي وتوثيق الفرق مع الصلاحية المناسبة.
7. **صلاحيات دقيقة:** الاستقبال لا يستطيع إنشاء قيود مالية أو تعديل فاتورة معتمدة؛ أمين الصندوق لا يستطيع تعديل الأسعار؛ المحاسب يعمل على التسويات وفق صلاحيات؛ المدير يوافق على العمليات عالية الأثر.
8. **تقرير المركز المالي:** التقارير مبنية على حركات وقيود منشورة لا على أرقام يدويا في لوحة التحكم. ربط كل بند بالقسم / مركز التكلفة.
9. **العملات:** إعداد عملة أساس وتعدد عملات عند الحاجة (YER / SAR / USD)، وسعر صرف معتمد لكل سند، وتقارير بعملة الأصل والأساس؛ لا تجمع أرصدة بعملات مختلفة بلا تحويل موثق.
10. **الخصوصية:** لا تعرض التشخيص والأعراض والوصفات للمحاسب أو أمين الصندوق إلا عند ضرورة معلنة. بيانات المرضى المالية منفصلة منطقيا عن السجل الطبي؛ النقل داخليا عبر HTTPS مع التحكم في الوصول والتدقيق.
11. **استمرارية التشغيل:** خادم واحد مركزي مسؤول عن الكتابة؛ أخطاء الشبكة لا تنشئ دفعا مكررا؛ استخدام معرف طلب فريد وإعادة الاستعلام عن النتيجة بعد انقطاع الاتصال.
12. **النسخ والاستعادة:** نسخة PostgreSQL مشفرة ومجدولة بعد اعتماد السياسة، مع فحص دوري للاستعادة على بيئة اختبار مستقلة وعدم تخزين المفاتيح في Git.

## 5. نماذج سير عمل المستخدم

### OPD — زيارة العيادات الخارجية

استقبال المريض > اختيار الطبيب والخدمة > إصدار فاتورة محددة البنود والسعر والتاريخ > اعتماد فاتورة > تسجيل قبض (كلي أو جزئي) > إصدار قسيمة زيارة/وصل مالي قابل للطباعة > تحديث كشف الصندوق والذمم وقيد المحاسبة > التقرير اليومي.

**مثال محاسبي تعليمي:** كشف 5,000 ريال يمني، قبض 3,000 والباقي 2,000. إصدار الفاتورة: مدين ذمم مرضى 5,000، دائن إيرادات عيادات 5,000. القبض: مدين الصندوق 3,000، دائن ذمم مرضى 3,000. الباقي 2,000، المقبوض 3,000، إيراد الفاتورة 5,000 لا 8,000.

### IPD — التنويم

قبول المريض > تخصيص غرفة وسرير > تسجيل رسوم الإقامة اليومية والخدمات > دفعات مقدمة إن لزم > النقل بين الغرف دون تكرار الأيام > معاينة كشف الحساب > إنهاء الإقامة وتثبيت تاريخ الخروج > فاتورة نهائية وتسوية المبالغ > صرف فاتورة وقسيمة خروج. **لا تصدر فاتورة نهائية مضاعفة عن الخدمات المفوترة سابقا.**

### القيود اليومية

تستعمل قيود اليومية للتسويات والاستهلاك والمخصصات والتحويلات والقيود الافتتاحية وغيرها، وليس لتحصيل فاتورة روتينية. تعرض الواجهة مجموعة حسابات قابلة للبحث وإضافة صفوف، مدين ودائن منفصلين، إجمالي الطرفين والفرق، وتمنع الترحيل حتى التوازن وتحقق الصلاحيات.

## 6. واجهة الاستخدام

- واجهة عربية كاملة RTL بخط عربي واضح، شريط جانبي ثابت مع ترتيب منطقي؛ نصوص إنجليزية للمصطلحات OPD/IPD عند الحاجة فقط.
- الوضعان الفاتح والداكن، مع الحفاظ على تباين النصوص ودلالات الألوان.
- نوافذ مرنة لا تخفي أزرار الحفظ والإلغاء، وتسمح بالتنقل بلوحة المفاتيح والبحث السريع.
- جداول قابلة للفرز والترشيح وطباعة/تصدير النتائج المعروضة، بدون تحميل آلاف السجلات في خيط الواجهة.
- لوحة معلومات تفرق بصريا بين (فواتير اليوم، المقبوضات، المستردات، المصروفات، رصيد الصندوق، الذمم).
- قسائم OPD، فواتير المرضى، سندات القبض والصرف، كشف التنويم، كشف حساب مريض؛ هوية المستشفى قابلة للإعداد.

## 7. واجهة الخادم وقاعدة البيانات (مقترح للتوسع)

Entities: `Patient`, `Doctor`, `Department`, `ServiceCatalogItem`, `PriceVersion`, `OutpatientVisit`, `Admission`, `Ward`, `Room`, `Bed`, `AdmissionCharge`, `Invoice`, `InvoiceLine`, `Payment`, `PaymentAllocation`, `Refund`, `CashDrawer`, `CashShift`, `Expense`, `ChartAccount`, `JournalEntry`, `JournalLine`, `CostCenter`, `AuditEvent`, `User`, `Role`, `Currency`, `FxRate`, `Attachment`.

- معرفات immutable وعلاقات FK تمنع السجلات المالية اليتيمة.
- مبالغ `decimal` أو NUMERIC بدقة ثابتة مع ضبط كسور العملة؛ لا استخدام لـ `double` في العمليات المالية.
- مفاتيح فريدة للأرقام المرجعية ومفاتيح إعادة المحاولة idempotency.
- صفوف مراجعة وتدقيق غير قابلة للتعديل عبر واجهة العمل، مع صلاحيات قاعدة بيانات محدودة.
- نظام ترحيل schema migrations مرقم بدلا من `EnsureCreated` قبل ترقية أي قاعدة إنتاجية.

## 9. استراتيجية التنفيذ

### الدفعة A: تثبيت أساس 0.1.0

- تشغيل بناء Windows فعليا، ومعالجة أخطاء الاختبارات، وتكوين migrations مرقمة.
- إضافة اختبارات تكامل لـ PostgreSQL ونموذج قيود ودفعات ونماذج فواتير.
- حصر صلاحيات الوصول، واعتبار المستندات المعتمدة غير قابلة للتعديل المباشر.

### الدفعة B: OPD وتحسين الواجهات

- ملف المريض، دليل الطبيب والخدمات، زيارة OPD، التذكرة، الفاتورة، القبض، طباعة سند.
- لوحة مؤشرات فاتورة مقابل تحصيل، ورصيد المستحقات، وتقارير القسم.

### الدفعة C: IPD ومراكز التكلفة

- قبول وتنويم وإقامة يومية وخروج وحركة الأسرة مع الفوترة ومنع التكرارات.
- الإيرادات والمصروفات حسب المركز المالي والقسم.

### الدفعة D: المحاسبة المتقدمة

- دليل حسابات ورحلة القيد المزدوج والذمم، كشف الحساب والتقارير والمرتجعات والإقفال.
- ثم مشتريات وموردون وتأمين ورواتب وصيدلية وفق أولوية المؤسسة الفعلية.

### إجراءات GitHub الملزمة

- فرع تطوير مستقل لكل دفعة، وتبدأ اختبارات xUnit قبل تغيير منطق الأعمال.
- Windows Core وWindows Release يعملان بالتوازي عند رفع التغييرات.
- داخل Windows Release تنجح الاستعادة والبناء والاختبارات قبل أي تعبئة للـ Portable أو Installer.
- يضاف اختبار تكامل PostgreSQL وأمن وصلاحيات كاختبار مطلوب قبل الدمج.
- لا دمج إلى `main` إلا بعد نجاح كل الفحوص والبناء والتحقق من عدم تعارض التغييرات.

## 10. عناصر تحتاج اعتماد إدارة المستشفى لاحقا

اسم المستشفى والشعار، طبيعة المستشفى والأقسام، دليل الحسابات الافتتاحي، سياسة خصومات المرضى والإعفاء، أنواع الدفع والعملة الأساسية، التأمين والجهات الخيرية، آلية الموافقات، الاحتفاظ بالسجلات، طريقة النسخ الاحتياطي، والنماذج المطبوعة الرسمية. هذه إعدادات قابلة للتخصيص؛ لا نفرض قيما تخمينية على بيانات مالية حقيقية.
