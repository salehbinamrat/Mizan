# عزل الأقسام وصلاحيات الموظفين — ميزان الطبي

## الهدف
ينشئ مالك البرنامج الحسابات من نافذة **الإدارة والصلاحيات ← إدارة المستخدمين والأقسام**. لكل مستخدم تصنيف وظيفي (مسؤول قسم، استقبال، صندوق، محاسب، مسؤول عام، إدارة عامة)، لكن **التصنيف لا يمنح أي حق بذاته**. يسجل المالك الصلاحيات الفردية ونطاقها، ويستطيع تعديلها أو إيقاف الحساب لاحقا.

## نطاق المستخدم
- `SystemOwner`: حساب التهيئة الأساسي وحده، يدير الحسابات والأقسام وكل الوظائف. لا يمكن إنشاء حساب ثان بهذه الصفة من واجهة الإدارة أو تغيير هذا الحساب من شاشة المستخدمين.
- **مستخدم قسم واحد:** يتبع `DepartmentId` محددا، ويرى فقط بيانات هذا القسم، بشرط امتلاكه إذن العملية أيضا.
- **مسؤول عام مفوض:** `AllDepartments=true` دون `DepartmentId`، ويتصفح كل الأقسام فقط في الوحدات التي منحها المالك صراحة. ليس مالك النظام ولا يستطيع إنشاء مستخدمين أو إدارة الأقسام.
- **فشل آمن:** الحساب غير المعين لقسم والمحروم من نطاق الكل لا يرى سجلات التشغيل. البيانات القديمة بلا قسم لا تظهر للمستخدمين المقيدين.

## قائمة الصلاحيات المدارة
- المرضى: `patients.read` و`patients.create`.
- الخدمات: `services.read` و`services.manage` (الإضافة بالمرحلة الحالية).
- الصناديق: `desks.read` و`desks.manage`.
- المناوبات: `shifts.read` و`shifts.open` و`shifts.close`.
- الفواتير: `invoices.read` و`invoices.issue`.
- التحصيل: `receipts.create`.
- المصروفات: `expenses.create`.
- التقارير: `reports.read`.
- سجل العمليات: `audit.read`، ضمن نطاق القسم أو جميع الأقسام بحسب التفويض.
- `users.manage` و`departments.manage` **محجوزتان لمسؤول البرنامج فقط**، ولا يمكن تفويضهما في هذه المرحلة لمنع تصعيد الصلاحيات.

تتطلب الواجهة منح صلاحيات القراءة الملائمة لتنفيذ بعض العمليات؛ فمثلا إصدار فاتورة يحتاج عمليا `patients.read`, `services.read`, `invoices.issue`، والتحصيل يحتاج `invoices.read`, `shifts.read`, `receipts.create`، ولا تمنح هذه الصلاحيات تلقائيا.

## قواعد العزل من الخادم
- جميع مسارات API مؤمنة باستثناء تسجيل الدخول وHealth؛ سياسات ASP.NET Core تفحص منح الصلاحيات الحقيقية من قاعدة البيانات **مع كل طلب**، ولا تعتمد على الأزرار الظاهرة في تطبيق Windows.
- تصفية استعلامات المرضى والخدمات والصناديق والفواتير والتقارير والأحداث إلى القسم المسموح على مستوى قاعدة البيانات.
- الطلبات المباشرة بمعرف فاتورة خارج القسم تعود `404`، والعمليات التي تحاول تعيين قسم خارج نطاق المستخدم تعود `403`، والأعمال بلا إذن وظيفي تعود `403`.
- أي إصدار فاتورة يجب أن ترتبط كل أسطره بخدمات من قسم المريض نفسه في هذا الإصدار؛ يمنع خلط الأقسام دون إحالة أو تسوية معتمدة.
- مناوبة الصندوق مرتبطة بقسم الصندوق، ولا تقبل دفعات لفواتير تابعة لقسم آخر. لكل فاتورة وتحصيل ومصروف وقيد محاسبي وسجل تدقيق `DepartmentId` للفلترة والمتابعة.
- تغيير الصلاحيات أو القسم أو حالة النشاط أو إعادة ضبط كلمة المرور يلغي جلسات الموظف الجارية، ويتطلب دخولا جديدا.
- يتم توثيق إنشاء المستخدم وتغيير نطاقه وصلاحياته مع القيم السابقة واللاحقة، دون كلمات مرور.

## مثال عملي
- مدير المختبر: قسم LAB وصلاحيات عرض الخدمات والفواتير والتقارير. لا يرى بيانات الطوارئ أو صلاحيات موظفيها.
- موظف استقبال الطوارئ: قسم ER وصلاحيات تسجيل المرضى وإصدار الفواتير فقط؛ لا يرى الإيرادات العامة أو يعدل حقوق المستخدمين.
- محاسب عام: نطاق كل الأقسام مع صلاحية التقارير والفواتير؛ لا يستطيع الصرف أو استلام المبالغ ما لم تُمنح له تلك الحقوق.
- مالك البرنامج: جميع الأقسام والصلاحيات والمسؤول الوحيد عن تفويضها.

## حدود الإصدار الحالي
- السجل الأساسي للمريض مرتبط بقسم واحد. لا توجد بعد إدارة إحالة المرضى أو زيارات مشتركة بين الأقسام؛ يجب بناء كيان زيارات محمية قبل استخدامها في بيئة متعددة الأقسام فعليا.
- لا يوجد تعديل الخدمات أو سندات عكسية كاملة حاليا، حتى لو سميت الصلاحية `services.manage`.
- الترقيات من قاعدة قديمة **غير آلية**: `EnsureCreated` لا يضيف أعمدة ولا علاقات إلى الجداول القائمة. لا تطبق المشروع المعدل على قاعدة إنتاجية؛ استخدم نسخة تجريبية فارغة أو خطة EF migrations موثقة بعد نسخ احتياطي ومراجعة ترحيل البيانات إلى الأقسام. لا تُمنح صلاحيات عامة تلقائيا للمستخدمين القدامى.
- إصدار المستشفى الفعلي مشروط باجتياز اختبارات .NET على Windows واختبارات API مع PostgreSQL والتزام كل صلاحيات القراءة والكتابة والعزل على كل المسارات.

## اختبارات القبول
1. مسؤول القسم A يرى فقط مرضى وخدمات وفواتير وتقرير A.
2. محاولة فتح فاتورة B بمعرف مباشر تعيد `404`.
3. محاولة إضافة مريض إلى B من حساب A تعيد `403`.
4. الدور `Admin` وحده لا يمنح صلاحية أو نطاق جميع الأقسام.
5. الحساب المفوض لجميع الأقسام يقرأ البيانات من الأقسام كلها في الوحدات المحددة فقط.
6. الموظف المفوض برؤية التقارير لا يستطيع إنشاء سند قبض أو إدارة الحسابات.
7. تعطيل الحساب وتغيير الصلاحيات وإعادة ضبط كلمة المرور يلغي الجلسات السابقة.
8. مالك البرنامج وحده يدير الحسابات والأقسام ولا يمكن تعديل ملكيته من الواجهة.
9. لا تسجل الفاتورة خدمات من قسم مختلف عن قسم المريض.
10. لا يقبل صندوق قسم دفع فاتورة من قسم آخر.

هذه الوثيقة تصف التنفيذ التجريبي؛ الاختبارات الفعلية لم تُشغّل بعد على .NET/Windows/PostgreSQL في بيئة الإنشاء.
